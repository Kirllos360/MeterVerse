## What this means
The solar calculation pipeline works (compute/persist/route tested) but **the directional register capture (OBIS 1.8.0/2.8.0 from a meter) is NOT persisted** — it is the OBIS-gated dependency (STATE 2, approval). The measurement model needs an OBIS decision before adding columns.

## Recommended canonical measurement model (DESIGNED, not implemented — OBIS-gated)
Given the existing Reading model is event-append with `unit` + `source` + `timestamp`, the minimal OBIS-compatible extension (NO new tables, additive columns):
```
Reading +=
  obisCode   String?   -- e.g. "1.8.0", "2.8.0", "3.8.0", "4.8.0"
  direction  String?   -- "import" | "export"
  registerType String? -- "active" | "reactive" | "apparent"
  multiplier Float?    -- scaling factor (default 1)
  channel    String?   -- OBIS channel when >1
```
This preserves the existing architecture (no second model, additive migration, future utility types: electricity/water/BTU/gas all via obisCode + unit).

## Why additive-only (evidence)
- Existing Reading is event-append (idempotency test proves append semantics).
- Solar engine already accepts directional values as input — the capture is the only gap.
- No new dependency; only an OBIS decision + additive migration.

## Decision required (APPROVAL / EVIDENCE)

2. Approve the additive column set above (or provide the canonical alternative).
